# ADR: secure AppImage prerequisites on restricted Linux hosts

**Status:** User experience selected; mechanisms proposed for independent security review. No privileged implementation or host modification yet.
**Date:** 2026-11-02
**Decision owner:** The user delegates routine implementation decisions. The mechanisms below are engineering decisions for review, not additional preference questions.
**Plan:** [Implementation plan](../plans/2026-11-02-dilla-linux-sandbox.md).

## Native-package scope amendment

The user's later .deb/.rpm/AUR request supersedes the earlier package-format non-goal. The [native-package design](2026-11-02-dilla-linux-native-packages-design.md) and [plan](../plans/2026-11-02-dilla-linux-native-packages.md) define that additional scope. AppImage's fixed ownership root is now /usr/lib/dilla/appimage; native packages use sibling /usr/lib/dilla/native. Their common /usr/lib/dilla parent is root-owned 0755 and validated, but emptiness/authority checks apply to the selected ownership leaf, never its sibling. Neither owner changes or recursively removes the other leaf or shared parent. The single-helper/floor rules below apply within the AppImage domain; a package-owned helper has an independent persistent floor and only its package manager may change it. The same component-generation numbering is reused, without claiming one owner revokes the other's installed helper. Task 1's framing, signature domain, bounds and pure validation contract are unchanged.

## Outcome and evidence

Keep AppImage distribution, default Ubuntu support, renderer sandboxing and automatic verified application updates. Determine prerequisites automatically and use the normal desktop administrator prompt only when a secure system component needs installation/maintenance. People do not choose namespace mechanisms, paths, helper versions or shell commands. There is no unsandboxed mode.

The unsafe builder fallback is already removed. Normal FUSE upgrade/recovery passed on a namespace-enabled host. Restricted Ubuntu instead aborts in `setuid_sandbox_host.cc:172`: the mounted adjacent helper fails root ownership/mode 4755 validation, despite the prepared external `CHROME_DEVEL_SANDBOX`. Canonical run 41407078511/artifact 13123654078 directly reproduces this before any update outcome. Missing metadata reports are downstream symptoms. Do not disable AppArmor/user namespaces, change signing/mount protections, or substitute extraction for mounted acceptance.

## Decision and alternatives

Use one machine-wide Chromium helper at `/usr/lib/dilla/appimage/chrome-sandbox`, maintained by a root-owned **non-setuid** offline program. The adjacent AppImage helper becomes an absolute symlink to that location, preserved in SquashFS. All users, channels, retained applications and recovery/watchdog copies share the current compatible helper. No old privileged helper version is retained.

Namespace-only support would exclude the failing Ubuntu configuration. Native .deb/.rpm/AUR distribution is now selected in the [native-package design](2026-11-02-dilla-linux-native-packages-design.md); this ADR governs the AppImage ownership domain. A custom permanently-setuid broker adds a privileged runtime protocol. Those alternatives are not selected. Direct `pkexec(userOwnedPath)` is rejected: hashing a pathname before authentication does not bind the subsequently executed inode.

Use separate unprivileged native launch/setup and root maintainer executables, built with the existing Go toolchain/standard cryptography and existing `x/sys/unix` syscall dependency. The maintainer is `CGO_ENABLED=0` and never links/loads GUI libraries; only the unprivileged frontend may link the existing desktop GTK3 prerequisite for fixed explanatory UI. Never run Electron as root. No daemon, privileged networking or renderer filesystem/shell capability is introduced.

## First-install authorization: immutable bootstrap

Before authentication, the frontend constructs this argv array **without a shell**:

```
/usr/bin/pkexec --disable-internal-agent /usr/bin/python3 -I -S -c <literal bootstrap-v1 program>
```

The literal program contains the exact compiled capsule length/SHA512 and native-maintainer offset/length/SHA512. None is renderer-, environment- or manifest-selected. The kernel copies argv before the prompt. The privileged executable is the distribution-managed interpreter, not a scratch executable. `-I -S`, fixed working directory and cleared environment exclude user Python modules/site initialization. Subsequent maintenance normally invokes the installed native program instead.

The frontend writes the embedded capsule to stdin and closes its pipe. The literal bootstrap follows this exact dispatch order under the root-only lock. Across descriptor-exec, duplicate the already locked open-file-description to fixed FD 3, mark that descriptor inheritable for this single exec and close duplicate lock handles. Native entry validates FD 3 against the pinned canonical root-owned0600 lock inode, checks read/write access and obtains `flock(LOCK_EX|LOCK_NB)` on **that same descriptor** (idempotent for the inherited open-file-description). It must not reopen/acquire a second lock while holding the first. Set FD 3 close-on-exec again immediately; close/release it only after recovery/transaction ends. With no valid handoff descriptor, normal installed entry opens/acquires the same fixed lock itself. Unexpected handoff identity/access errors fail closed, never create a parallel lock. This prevents both an unlock interval and self-deadlock.

1. Require effective UID 0 and no positional configuration. Pin canonical trusted root-owned/non-writable system ancestors by directory FD; reject unsafe ownership, ACLs, symlinks and special files. All descendants and recovery names are fixed constants, never read as paths from input/records.
2. **Resident exists:** pin/check its owner, non-setuid mode and hash against the recognized current receipt or authenticated pending old/new-maintainer identities; descriptor-exec it. It first recognizes validated terminal commit/cleanup as defined below, then recovers any nonterminal authority before accepting new input. A matching committed receipt does not require bootstrap stages that terminal cleanup already removed. Never execute the incoming maintainer or reset floor/history.
3. **Resident missing, durable first-install bootstrap anchor exists and no validated terminal receipt/current-component pair exists:** read the bounded root-owned anchor, pin its fixed protected `bootstrap-maintainer` and `bootstrap-capsule` files, verify exact sizes/SHA512/device/inodes and root-only ownership. Descriptor-exec **that previously accepted staged ELF**, with the already protected capsule on FD 0. Incoming bytes/compiled older digests cannot replace the anchor. This is the only missing-resident recovery exception. Missing/mismatched stage, non-initial intent or unknown state holds for repair; it never falls back to incoming code.
4. **No prior authority:** only a genuinely empty state namespace (or exact unreferenced, nonprivileged bootstrap stages left before anchor durability) can start first install. Preserve unknown children; never reinterpret receipt/tombstone/install/remove history as empty. Create new root-private 0700 staging directory and `O_EXCL|O_NOFOLLOW` regular capsule file. Copy exactly the literal byte count, then require EOF using one excess-byte check; absolute 30-second input deadline and bounded memory. Truncated/excess/stalled input publishes no authority. No ordinary user ever has a writable FD to protected bytes.
5. Verify capsule SHA512, fsync, close writable handles, reopen read-only/check inode identity. Copy/hash/fsync the native-maintainer slice identified by literal offset/length/hash into `bootstrap-maintainer`, close its writable handles and retain its protected directory entry. Validate the literal initial tuple/date window against current time **before writing any admission anchor** (expired/future material must not acquire historical acceptedAt authority). Atomically publish/fsync the initial-bootstrap anchor and its directory **before** any descriptor exec or resident publication. From this point the anchor contributes to the floor and only its accepted bytes may finish initial setup. Descriptor-exec the protected staged ELF with protected capsule FD 0; it may atomically publish/fsync the resident maintainer, then begin the install transaction below. Keep bootstrap stages/anchor until the resident, initial receipt and retirement are durable.

The bootstrap never unpacks an archive, evaluates input, imports input code or follows an input-selected path. On existing anchored recovery it need not copy new input or allocate new payloads: close/ignore the incoming pipe and use prior protected data. The frontend tolerates EPIPE **only** when the child completes successfully and a fresh ready-state check confirms the requested requirement; otherwise preserve the actual error. This prevents disk-full recovery from depending on copying another incoming capsule.
Linux FD-exec is required; no mutable-path or `ETXTBSY` workaround is allowed. Pass fixed argv/minimal environment, close unintended FDs, and exclude AppImage loader variables, credentials, deep links and update activation markers.

**Authorization scope:** first installation still assumes the administrator chose an authentic AppImage, as for a downloaded installer. Frozen code/digests prevent prompt-time pathname substitution; they cannot authenticate a frontend already replaced before invocation. The first OS dialog identifies `/usr/bin/python3`, not a cryptographically app-specific polkit action. The unprivileged frontend shows a fixed native GTK3 explanation before that normal prompt; no remote content is loaded and the root process has no GUI. GTK3 is already an Electron desktop prerequisite; binding this small fixed dialog and its availability must be proved on supported Ubuntu rather than installing a new GUI framework. No blanket Python policy, new permissive polkit rule, retained authorization or `auth_admin_keep` is installed. Missing distro Python/pkexec/session agent is an actionable prerequisite error, never a PATH/shell fallback.

Later authorization invokes only `/usr/bin/pkexec --disable-internal-agent /usr/lib/dilla/appimage/sandbox-maintainer`. It accepts a dedicated-signature-authorized constrained capsule; unsigned first-install data never authorizes a resident update. Cancellation and authorization failure remain distinct (126/127); Dilla never handles the password. Branded polkit policy is outside this design and not necessary for correctness.

## Capsule, signature and freshness

The capsule is fixed framing, **not an archive**: eight-byte magic `DLSBOX1\0`; little-endian u32 manifest length, u32 signature length, u64 maintainer length, u64 helper length; then those four byte strings in order. Limits: manifest 64 KiB, signature exactly 64 bytes for resident maintenance (zero only for the initial embedded form described below), maintainer 32 MiB, helper 8 MiB, total 48 MiB. Require positive manifest/maintainer/helper lengths and exact EOF; only the explicitly initial signature may be empty. No compression, paths, filenames, arguments or extension records.

Ed25519 signs `Dilla Linux sandbox capsule v1\0` followed by exact manifest bytes. Compile a dedicated public sandbox-maintenance key set into frontend/maintainer/public release trust. Private maintenance signing stays outside source/CI; ordinary application metadata signing does not authorize new root code. Existing installed trust authorizes subsequent maintainer replacement/rotation; input-supplied keys never do. All-key loss requires separately trusted repair.

Exact manifest fields:

```
{format:1,kind:"dilla-linux-sandbox",generation,platform:"linux",arch:"x64",
 compatibilityEpoch:1,sandboxApi:1,publishedAt,expiresAt,
 maintainer:{size,sha512},helper:{size,sha512}}
```

Reject unknown/duplicate/case-aliased fields, noncanonical base64, unsafe integers, non-UTC dates, length/hash/ELF-architecture mismatches. Generation is positive and **machine-wide across stable/beta**. Component publication timestamps/configuration are immutable per generation, not regenerated from each application build clock. Build the maintainer reproducibly with `-trimpath -buildvcs=false` and stable component-only configuration; app version/commit is not embedded into it. Reuse identical component bytes across app releases until a genuine component/generation change. Any changed maintainer/helper/manifest bytes require a new generation, even a toolchain-only change; renew an expiring component as a new generation rather than silently re-date it. Same generation requires identical manifest and both component hashes; different bytes require a higher generation. First release remains Linux x64; arm64 requires separate actual native qualification.

First installation requires the exact compiled initial digest tuple plus normal administrator approval; a resident generation increase requires a valid dedicated maintenance signature. Both require unexpired dates: maximum 93-day envelope, maximum five-minute future skew. Committed helpers remain usable offline after the envelope expires; expired material cannot introduce new privileged code. Signed application releases raise required minimum generations for security fixes. This provides no offline revocation oracle. Trust root clock/history; complete disk rollback, root compromise and already-exploited privileged processes are outside its guarantees. Preserve maximum accepted time/floor, rejecting maintenance that depends on rolling the clock behind recorded history.

## Compatibility and application trust

Epoch 1 means every helper released in that epoch supports **all publicly released runtimes in it**, across users/channels, including old parents, watchdogs and retained rollback applications. Chromium `--get-api` equality (currently 1) is necessary, insufficient evidence. Qualify actual helper/runtime pairs. A helper ABI/epoch change blocks publication until a separately reviewed migration exists; never keep an old vulnerable setuid version to satisfy rollback.

### Exact release order: no signature-in-artifact rebuild

Preserve **build accepted CI artifacts → offline component/feed signing → publish those exact bytes**. Production private keys never enter CI. There is no pre-signed capsule hidden inside a build or post-acceptance AppImage modification.

1. CI builds the final native maintainer and pinned helper, emits the strict unsigned component manifest plus framed capsule with signature length zero, then builds the frontend/AppImage embedding those exact bytes. The maintainer compiles its initial helper hash/generation/epoch/API/dates and public maintenance keys; it does not embed its own hash. At genuine first installation it also verifies that the supplied manifest's maintainer hash equals its own protected executable hash. This avoids self-hash circularity.
2. This unsigned embedded form is usable **only at the first-install trust point**: authenticated-as-chosen AppImage, frozen bootstrap hashes, normal administrator approval, no existing committed root state. Write a root-owned initial-digest receipt/floor. It cannot overwrite/reset resident or removed state, regardless of fresh approval or newer application version. State recovery never treats unsigned data as a new resident generation.
3. CI publishes accepted `dilla-${version}-linux-x64.AppImage`, exact `dilla-${version}-linux-x64.sandbox` raw capsule, exact `dilla-${version}-linux-x64.sandbox.json` manifest and build/compatibility proof as unsigned candidate artifacts. Native acceptance uses ephemeral compile-distinct fixture keys for signature-positive/fault scenarios; no production private key is read. Production initial-digest behavior and final exact component hashes still need their native/provenance checks.
4. The final offline signer verifies all existing release gates, component provenance/hash/epoch/generation and source/SHA/run. It signs the **exact accepted manifest bytes** with the dedicated maintenance key and emits `dilla-${version}-linux-x64.sandbox.sig` as canonical base64 Ed25519 text (64 decoded bytes). It signs the app feed binding the accepted AppImage/capsule/manifest/signature assets. It never rebuilds/patches/recompresses any executable, capsule or AppImage; a failed check requires a fresh CI candidate rather than a metadata override.
5. The unprivileged updater downloads/caches those bounded public signed records with the verified candidate before asking for authorization. For resident maintenance it supplies the exact embedded/raw capsule components plus the detached 64-byte signature in the fixed privileged framing. Its proof of authority is the dedicated signature, never the application's unsigned descriptor/hash. The root maintainer verifies it under installed keys/floor before changing root code.

Initial single-AppImage setup therefore works offline from its compiled trust point. Later offline maintenance works after the public detached signature was cached/downloaded with the update; the helper payload itself remains embedded and the privileged process never fetches it. A newer manually downloaded AppImage automatically fetches its fixed public sidecars when online; nobody must locate a signature manually. URLs derive solely from the compiled version/arch and approved GitHub release path, with HTTPS/standard port, no cookies/credentials, at most three redirects to the existing explicitly approved GitHub release-asset hosts, an overall 10-second fetch bound, and the response caps below. Compare detached manifest to embedded bytes and verify the dedicated signature before authorization. A lone newer AppImage cannot update a resident helper offline without its previously cached signed sidecar. Offline/signature/auth failures preserve the working parent, candidate and account data with a clear retry; do not accept unsigned updates or imply universal single-file offline maintenance. Ordinary automatic updates fetch/cache the sidecar before becoming ready.

The authenticated Linux artifact adds:

```
linuxSandbox:{compatibilityEpoch:1,minimumGeneration,
 bundle:{url,size,sha512}}
```

Pin bundle URL to the approved GitHub release/version and fixed `.sandbox` asset name. The AppImage embeds the identical unsigned raw capsule and its own compiled epoch/minimum. The detached signature remains a separately authenticated release asset. Derive `.sandbox.json` and `.sandbox.sig` from the fixed capsule basename on the same approved release origin; authenticate all three names/sizes/SHA512 in the existing signed `release.assets` list (preserve all seven original platform assets plus these three separately required component assets). CI uploads capsule+manifest; only the final offline signer adds the signature asset. Updater bounds are 64 KiB for manifest and 89 bytes for canonical signature text (optional final newline), and it must confirm detached manifest bytes equal the capsule manifest before becoming ready. Publisher checks external/embedded component equality, dedicated signature, all hashes, version requirements and native compatibility proofs. The root maintainer re-verifies the helper signature; it does no networking. App rollback retains the newer compatible system helper, never decreases its floor.

## Fixed system layout and status

| Object under `/usr/lib/dilla/appimage/` | Ownership/mode | Meaning |
|---|---|---|
| Parent directory | root:root 0755 | Pinned trusted ancestor, no writable ACL |
| `sandbox-maintainer` | root:root 0755, one link | Non-setuid fixed maintenance entry |
| `chrome-sandbox` | root:root 4755, one link | Sole published privileged helper |
| `sandbox-receipt.json` | root:root 0644 | Initial digest anchor or signed manifest, acceptedAt, maximum generation, hashes, active/removed state |
| `sandbox-transaction.json` | root:root 0644 | Durable authenticated intent and expected inode identities; no caller paths |
| `.sandbox-staging/bootstrap-anchor.json` | root:root 0600 | Durable first-install authority for fixed staged maintainer/capsule identities |
| `.sandbox-staging/` | root:root 0700 | Same-filesystem new files/prepared receipt/demoted retired inode |
| `.sandbox-lock` | root:root 0600 | Root-only transaction lock; ordinary users cannot hold it |

Use directory-relative operations from pinned trusted system roots. Distro canonical `/usr` aliases require one explicitly tested canonical-root derivation, not arbitrary following of symlinks. Reject unexpected symlinks, hardlinks, writable ACLs, capabilities, special files, mount/device transitions and unsupported durability. No recursive deletion outside exact known transaction children.

The unprivileged fixed `--check` role returns at most 4 KiB JSON: protocol/status (`missing`, `ready`, `maintenance`, `removed`, `unsafe`), generation, epoch, API and public hashes. Check actual helper ownership/mode/hash and receipt; observe transaction/receipt before and after and fail safely on races. No profile access, writes, permission changes or user-accessible lock. Only complete ready state satisfies a managed prerequisite; environment variables supply no authority.

The privileged no-argument role consumes the capsule on stdin. The only other mutation role, fixed `--remove`, demotes/fsyncs/unlinks the current helper while retaining the generation tombstone and non-setuid maintainer. No paths/options/reset operation. Removing an AppImage never silently removes this shared component. Tombstone-aware reinstall enforces the floor; no application/account state is touched.

## Root transactions and precise authority records

Hold the root-only lock plus open directory/file FDs throughout. Recover existing authenticated intent first (root-owned initial anchor or dedicated maintenance signature). An authenticated durable intent contributes to the floor before receipt promotion. Capture identity from open FDs, not lazily from a pathname after renaming it. Records never select a path/command.

The bounded exact record contracts are:

- **Initial anchor:** `{format:1,kind:"dilla-linux-sandbox-bootstrap",operation:"initial",generation,acceptedAt,manifestSha512,compatibilityEpoch:1,sandboxApi:1,capsule:{size,sha512,device,inode},maintainer:{size,sha512,device,inode}}`. Root ownership plus the frozen first-install bootstrap authorizes this initial tuple. `capsule` and `maintainer` always name fixed protected bootstrap stages, not strings from the record. Maximum record size is 4 KiB; duplicate/unknown fields or unsafe integer encodings fail. This authority exists even before a resident/receipt exists.
- **Install intent:** `{format:1,operation:"install",generation,acceptedAt,authorization,manifest,signature,oldMaintainer,newMaintainer,oldHelper,newHelper,previousReceiptSha512}`. `authorization` is `initial-anchor` or `maintenance-signature`; component identities are fixed `{size,sha512,device,inode}` or null for absent old components. The initial form must bind the exact durable bootstrap anchor. The resident form verifies the dedicated signature. Stage/receipt names are fixed constants. Intent size is at most 128 KiB including the bounded manifest; no new key or filename is allowed.
- **Removal intent:** `{format:1,operation:"remove",maximumGeneration,acceptedAt,previousReceiptSha512,currentMaintainer,currentHelper}`. It derives authority/floor from the existing validated root receipt/intent and normal administrator authorization; no new executable is introduced. Same 4 KiB bound and fixed identities, no incoming capsule required.
- **Receipt:** records authorization kind (`initial-digest` or `maintenance-signature`), immutable initial anchor digest, exact accepted manifest/signature if applicable, `acceptedAt`, `maximumGeneration`, current maintainer/helper hashes, epoch/API and `state:"active"|"removed"`, `completedOperation:"install"|"remove"`, plus `transactionSha512` binding the exact immutable intent. Initial receipts additionally bind the immutable bootstrap-anchor digest. A removed receipt retains previous hashes/floor; a missing current helper is expected there. All entries are root-owned bounded regular files.

### Install ordering

1. **STAGED:** verify resident signature (or exact genuine initial anchor), acceptance-time expiry, floor/epoch and component bytes; copy/hash/fsync new private inodes. Fully prepare/fsync/close the next receipt. Persist/fsync authenticated install intent and containing directories. Allocation-heavy work precedes old-helper revocation; ENOSPC here leaves the working helper unchanged. An initial bootstrap anchor already makes a pre-resident interruption repairable.
2. **MAINTAINER-PUBLISHED:** atomically publish the authenticated new **non-setuid** maintainer and fsync its directory **before helper revocation and before publishing the new receipt**. Retain exact old nonprivileged maintainer bytes until cleanup. On first install this publishes the staged anchored ELF. The current executing maintainer keeps its pinned handles/lock; replacing its pathname does not change the process running the transaction.
3. **REVOKED:** pin/hash the exact old helper; `fchmod` through its FD removes both SUID/SGID bits; `fstat` verifies; fsync inode metadata. Retain the demoted inode/FD. Uncertain chmod/fsync holds; never restore old privilege. Progress-phase writes are advisory: recovery inspects actual signed intent, pinned hashes and modes.
4. **HELPER-PUBLISHED:** set new authenticated helper root:root 4755 while private, verify/fsync, then same-device `renameat2(RENAME_EXCHANGE)` (or no-replace first install); fsync both directories. Old inode was already demoted, so later exec via an old FD cannot gain setuid. Rename-first/chmod-later is forbidden.
5. **COMMITTED:** only after **both new component paths and directories are durably correct**, atomically publish/fsync the prepared receipt. Receipt cannot durably name new maintainer while normal ordering leaves the old pathname. Before commit, old receipt + new maintainer is expected and means maintenance, not downgrade permission. Install intent authenticates both recognized maintainer identities; either protocol-compatible old/new executable can recover its fixed staged state. Every maintainer replacement must understand the prior receipt/intent schema and trust chain. For key rotation, its compiled verification set must retain the old signing key needed by the admitted transaction and existing receipt, not only the new key. First-release maintenance permits overlapping key addition; retiring a still-needed key requires a separately reviewed migration, not silently dropping it. Incompatible protocol/trust migration is a release blocker.
6. **RETIRED:** verify displaced helper lacks SUID/SGID/capabilities, unlink only exact demoted helper/old nonprivileged maintainer stages and fsync. After receipt/components agree, clear/fsync install intent; for first install remove/fsync bootstrap stages/anchor **last**. Once that terminal receipt is validated, deletion of these exact cleanup children is idempotent: ENOENT is already cleaned, never a missing-authority failure. Only then report success. Publication/flush uncertainty remains repair state, never generation rollback.

### Removal ordering

First recover any prior authorized operation; do not silently supersede it. Prepare/fsync a removed-state tombstone receipt preserving the maximum floor. Persist/fsync **REMOVE-STAGED** intent before permission/path changes. Demote/fsync the exact current helper inode (**REMOVE-REVOKED**), unlink its canonical entry and fsync directory (**REMOVE-UNLINKED**), then atomically publish/fsync prepared tombstone (**REMOVE-COMMITTED**). Keep the recognized non-setuid maintainer for future signed repair/reinstall. Clear/fsync removal intent last. A missing helper after REMOVE-UNLINKED is expected, not corrupt installation and never a reason to restore privilege. Retry finishes the tombstone without requiring the missing helper or a new capsule. No profile/account data is touched.

### Recovery and accepted-time expiry

**Terminal recognition precedes pending-stage validation.** First validate the root-owned committed receipt, its initial/signature trust and maximum floor, both current component identities/hashes/modes (or expected absent helper for removed state), and any remaining intent's exact `transactionSha512`/operation/generation. A later/different/unknown pending intent cannot be suppressed by an older receipt, even at the same generation. If this receipt proves that exact operation committed, it is the authority for cleanup; a leftover initial anchor must match its receipt-bound digest if present, but already-deleted anchor/stages are not required to be reopened, re-executed or revalidated. Idempotently delete only remaining exact fixed retired/bootstrap children, rejecting unexpected existing identities/modes and preserving unrelated files. Missing demoted/bootstrap cleanup entries mean success; fsync the affected directories and finish removing the matching intent/anchor. No existing unsigned capsule, stale anchor or older receipt gains new installation authority. Only **precommit** pending recovery requires all referenced executable/payload stages; its missing/mismatched-stage rule remains fail-closed.

The intent/anchor stores the privileged operation's acceptance time **after** validation and before mutation. Reverify its signature/digest binding against that recorded time and all current pinned stage hashes/floor. Exact previously accepted root-protected bytes may finish after envelope expiry; this resumes existing authority rather than accepting a new expired introduction. New/substitute input, changed hash or generation cannot inherit that acceptance time and must satisfy fresh expiry/signature checks. An expired pending operation with missing/mismatched protected bytes holds; no unsigned replacement, lower generation or old-helper re-privileging. Removal introduces no new code and may finish from its accepted root receipt independent of that original envelope's current expiry.

| Last durable boundary | Recovery action |
|---|---|
| No anchor/receipt/intent | Discard only exact unreferenced nonprivileged bootstrap stages; incoming frozen initial installation may begin |
| Initial anchor durable; resident absent | Verify/FD-exec **anchored protected staged maintainer and capsule**, never incoming replacement; resume first resident publication |
| First resident durable; initial receipt absent | Recognized resident resumes anchored initial install; preserve anchor/floor, never enter fresh-install/reset mode |
| Install intent; resident still old | Execute recognized old resident; publish staged signed new maintainer first |
| New maintainer; receipt/helper old | Execute recognized new resident using pending authenticated old/new identities; finish helper forward |
| Old helper demoted; new absent | Maintenance hold; publish authenticated staged new bytes; never re-privilege old |
| New helper/maintainer; receipt old | Verify both component paths/intent, then publish prepared receipt |
| Receipt new but component observed old/mismatched | Hold/repair against exact intent; never claim ready or choose an old generation; this is not a normal durable ordering |
| Valid terminal receipt + matching current components; cleanup/anchor clearing failed | Recognize exact committed operation first; idempotently remove remaining fixed demoted/bootstrap children, treating already-deleted stages/anchor as cleaned; clear matching intent/anchor without re-executing stages |
| REMOVE-STAGED or REMOVE-REVOKED | Finish demotion/unlink/tombstone under removal intent; never restore helper privilege |
| REMOVE-UNLINKED; old active receipt | Missing helper is expected; publish prepared removed tombstone preserving floor |
| REMOVE-COMMITTED; intent remains | Verify operation-bound tombstone/current non-setuid maintainer; missing helper/cleanup entries are expected; finish idempotent cleanup and clear matching intent |
| Precommit missing referenced stage, ambiguity, unsafe root or unknown schema | Actionable repair hold; no guessing, floor reset or ordinary account entry |

**Availability limitation:** no Linux operation atomically changes old inode permissions and replaces a different inode. Revoke-before-publish necessarily creates a security-first interval. An interruption there may require normal administrator authorization to finish maintenance on next startup. The existing parent is not quit and its app/data remain unchanged; a **fresh sandbox startup** may wait for repair. Do not promise a usable old helper at every crash boundary. Successful maintenance supports old/new/rollback runtime startup, and later app-update failure keeps that newer compatible helper.

Renaming/unlinking alone does not revoke open FDs. Chmod also cannot revoke credentials already granted to an in-flight exec or running process. The guarantee concerns future exec privilege from retained old FDs after revocation and absence of old privileged files after success, not undoing a previously exploited helper.

## Automatic startup and actual-quit integration

AppRun retains exact quoted arguments/AppDir environment and execs the unprivileged frontend. Exact internal setup/probe roles cannot be selected by a protocol URL or renderer command. It never adds sandbox-disabling flags or selects helpers through caller environment; remove `CHROME_DEVEL_SANDBOX` from its launch environment while preserving required AppDir library/data variables.

For compatible managed-ready state, exec ordinary Electron unchanged. Pending maintenance is repaired before normal account/UI entry. With **no managed helper**, run a content-free actual Electron sandbox probe, not clone/unshare: exact mounted executable, early dedicated role, fresh private scratch profile, bundled local document/preload, denied network/permissions, one-use owned parent pipe. An actual sandboxed renderer acknowledges only its exact owned frame's sandbox-active boolean. Probe entry precedes normal profile, worker, Keychain, updater, network and store initialization. Stop/wait the probe and remove its owned scratch before ordinary exec.

A successful probe permits ordinary startup **without helper installation or authorization**. Only an exact owned failed process plus a pinned Chromium sandbox-initialization fatal, without a valid acknowledgement, selects secure setup. Other crashes/timeouts do not trigger elevation. Probe bound is 10 seconds. After successful setup, verify ready state and repeat the same probe once, then exec normal Electron; cancellation/error opens no ordinary account and offers retry. This extra cold-start cost on unmanaged namespace hosts must be benchmarked against existing performance gates. Actual probe execution context/AppArmor equivalence and missing-helper symlink behavior are implementation feasibility gates, not assumptions or reasons to weaken sandboxing.

Strict watchdog/health/recovered roles do not prompt or run the ordinary probe. If managed state exists, they require compatible ready state and fail closed if changed. If the entire managed namespace is absent, they exec Electron unchanged and let its actual namespace sandbox succeed or fail; no marker claims sandbox success or disables a protection. Thus namespace-only installations still update without installing a system helper. They cannot authorize system maintenance after parent exit. They still run Chromium with sandboxing intact. This preserves existing PID/group ownership and launch-marker checks; the frontend ultimately execs the real Electron process rather than adding an untracked long-lived coordinator.

Before an application update, download/verify candidates automatically. On **actual quit/restart**, first collect current call/recovering-call/draft/attachment guards. Prepare the candidate's prerequisite while the old parent holds single-instance authority and before arming `NativeQuitInstaller`. Cancellation/error leaves it running. After asynchronous authorization, reverify candidate bytes and collect **fresh guards again**, preserving late unload veto.
