# Bot v2: sealed commands, app requests over the socket, webhooks — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Bot answers a command in one round trip and starts music in about a second. It does this through sealed commands over the gateway, a supervised child process on a local socket, Bot channels and webhooks. Every authenticated app request moves onto the same socket, and the per-device interaction machinery and automod are deleted.

**Architecture:** the work is in eight phases. (A) Wire 6 and a generic `request`/`response` frame dispatched to the existing HTTP handlers. Each moved route is deleted from HTTP in the task that moves it. (B) HPKE sealed commands in the Rust core: client side in the wasm core, Bot side in `dilla-bot-core`, so Bot keys never enter Go or dillad. (C) dillad gets the catalog, the command key, the sealed relay, hints, webhooks and Bot channels. It also gets a capability-holding keeper process that starts the Bot as user `dillabot` on a dillad-owned Unix socket, with an event feed that can resume. (D) The Bot runs intake, authorisation and membership trust from pushed events, with zero per-command reads. (E) Music fast path. (F) The client: catalog cache, picker, sealed commands, fetches driven by hints, admin UI. (G) v1 is deleted and the migration runs. (H) Docs. Every task leaves `go test`, `cargo test`, vitest and the touched desktop e2e specs green. Each task updates the e2e specs its change breaks.

**Tech Stack:** Go (dillad, dillabot), Rust (core/dilla-core, core/dilla-bot-core, core/dilla-core-wasm; HPKE through the `hpke-rs` 0.8 already in `Cargo.lock` via `openmls_rust_crypto`), TypeScript/React (packages/client-core, packages/web), Playwright Electron lanes (e2e), SQLite + Postgres migrations with sqlc, systemd units and shell installers (deploy/).

## Global Constraints

- One branch and one PR. Release order: dillad and dillabot first, then the desktop app.
- **Wire 6 with no compatibility:** dillad refuses a wire-5-or-older negotiate or identify with `E_UPGRADE_REQUIRED`. The desktop app shows "Update dilla to continue" with its update button. A browser tab reloads. The Bot negotiates 6 too.
- **No REST fallback:** a moved route's REST form is deleted from the server, the route table, the protocol docs and the REST-only tests. Tests drive the socket. While the socket is down the app queues requests (mutations keep their ids) and sends them in order after reconnect.
- **Stays on HTTP** (spec list, verbatim classes): before a session exists (sign-in, passkey, TOTP, recovery, enrollment, session ticket for the socket); large binary bodies (blob upload and download); unauthenticated or public (`/v1/instance`, invite preview, web assets, desktop downloads, `/healthz`, incoming webhooks). Plan rulings add three (see "Rulings"): `POST /v1/sessions/negotiate`, the `F` allow-list routes an owed account uses before it has a socket, and the backup chunk and GIF media routes (bodies up to 1 MiB, above the 197120-byte frame).
- In-flight cap per connection: **64**. Over the cap the server answers `E_BUSY` and the client queues.
- Sealed requests: HPKE (RFC 9180) base mode, DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-128-GCM (suite `0x0020/0x0001/0x0001`, the suite the core already standardises in `CIPHERSUITE = MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`). The request is signed with the device identity key (DSK, Ed25519).
- Timing values, verbatim from the spec. Sealed-request timeout **5 s**. Offline reply drop **2 min**. Key rotation **weekly** with a **24 h** overlap. Dedupe **5 min**. `sent_at` window **2 min**. Hint coalescing **250 ms**. Health probe every **60 s**. Degraded after **2 failed probes**, a request waiting **more than 10 s**, or a queue growing for **60 s**. Bot restart ready within **5 s**.
- Webhooks: `POST https://<instance>/hooks/<id>/<secret>` with JSON `{"text": "...", "username"?: "...", "avatar_url"?: "..."}`, at most **4000 bytes** of text. Rate limit **30/min, burst 5**. `204` once the Bot accepts. The secret is stored hashed and compared in constant time. The body is never stored. The target must be a Bot channel.
- Music: lookups cached **6 h**. The next track is pre-resolved and pre-buffered at most **30 s** before the current one ends. Opus **48 kHz, 20 ms** frames from **one** ffmpeg. The Bot shows the **last 20** start timings.
- Targets, as automated tests. G2: Enter → first answer ≤ **RTT + 100 ms** at p95. G3: new track first frame **p50 ≤ 1 s, p95 ≤ 2 s**; next queued track gap **≤ 150 ms**; repeated track **p95 ≤ 500 ms**. Webhook POST → visible **≤ 500 ms p95**. Load: **200 members / 600 devices**, **0 device-list reads per command**.
- Anti-goals are acceptance criteria. No timer-driven or per-command per-member/per-device work. No health signal that can't fail. No client polling for a Bot answer. No stale pushed catalog. No plaintext command args, replies or reminder text stored on or readable by dillad.
- UI copy: the word "encrypted" (and the other words in `scripts/check-ui-copy.mjs`) is banned in UI files, comments included. `npm run check:copy` must pass.

### Rulings on spec contradictions (applied throughout)

1. Spec "Sealed commands" says "It POSTs the sealed request to dillad". Decision 12 and "App requests over the socket" put Bot commands on the socket. Ruling: the sealed request is the route `POST /v1/communities/{community}/bot/commands`, registered socket-only and sent as a `request` frame. There is no HTTPS form.
2. Spec "Measurement" asks that a socket request cost no more than "its REST form on the same connection", but REST forms are deleted and "a tests-only REST path is not kept either". Ruling: the comparison is a Go test, `TestSocketRequestCostsNoMoreThanHTTP` in `internal/api/socket_dispatch_test.go`. Inside the test it mounts the same handler on an `httptest` server and compares the two. Nothing is served in production.
3. Spec "Bot connection" says the socket is "created by dillad and passed to the child", and also requires reconnect and resume. A socketpair cannot be reopened. Ruling: dillad creates a listening Unix socket in its runtime dir (`/run/dillad/bot/gateway.sock`, dir `0750 dillad:dillabot`, socket `0660`). It passes the path, plus a one-time launch token over inherited fd 3, to the child. It accepts only peers whose `SO_PEERCRED` uid is the configured Bot uid and who present the launch token. There is no network path and no URL.
4. "Own OS user `dillabot`" needs `CAP_SETUID`/`CAP_SETGID`, which `dilla.service` lacks. Ruling: a minimal keeper process (`dillad bot-keeper`, re-exec'd before serving) keeps those two capabilities and only starts or stops the Bot on pipe commands. The serving dillad drops both from every capability set before it opens a listener. The Bot's sandbox needs bubblewrap, so `dilla.service` adopts the dillabot unit's `DevicePolicy=closed` instead of `PrivateDevices=yes` and drops `RestrictSUIDSGID=yes`. Task 11 records why in the unit comments.

## Review Focus

1. **A mutation in flight when the socket drops** (a message send, a sealed command, a role change). It is sent once more on the new connection with the same id. The result is exactly one effect and one answer, never a duplicate and never a silent loss. Owner: Task 3 (`a mutation in flight across a reconnect is applied once`). Task 2 adds the server half.
2. **A stale command key.** The client sealed to a key the Bot has since rotated. Within 24 h the Bot still opens it. After that the client gets `E_BOT_KEY_STALE`, refetches the catalog once and resends with the same `request_id`. It never loops. Owner: Task 15 (Bot) and Task 20 (client).
3. **A webhook POST while the Bot is restarting or offline.** It gets `503` with `Retry-After`, never `204`, and the body is never written anywhere. Owner: Task 13.
4. **A device revoked mid-session.** Its next command is refused. The user's other devices keep working. Only that user's leaves are re-checked, and no other user's events are held. Owner: Task 16.
5. **An admin unmarks a Bot channel that a feature or webhook targets.** The feature shows "needs a Bot channel" and posts nothing. The webhook answers `409 E_NOT_BOT_CHANNEL`. The Bot leaves the channel group. Owner: Task 9 (server), Task 17 (Bot), Task 22 (UI).
