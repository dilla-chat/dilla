# dilla v0.1.0-bot2.1

A fix release on top of [v0.1.0-bot2](v0.1.0-bot2.md). It fixes a Bot that stops answering commands after an upgrade
from v1 and never recovers. The release includes `dillad` with the web client, the Bot and its helper. Desktop
0.1.0-beta.4 stays current: there is no new desktop app.

**Upgrade if you run the Bot.** On an instance upgraded from v1, bot2 can lose the Bot's helper on its first start, and
every Bot command then fails until you upgrade.

## What's fixed

- **The Bot recovers when its helper stops.** The Bot keeps its keys and groups in a helper process. On bot2, a helper
  that stopped was never started again. Every command failed, and the log said `helper client is closed` every 10
  seconds until someone restarted the server. The Bot now starts a new helper within about 10 seconds. If the new
  helper stops again, the Bot waits longer before each new start, up to 5 minutes.
- **The first start after a v1 upgrade gets the time it needs.** On that start the helper removes the v1 Bot's
  per-member groups from its store. On a store that has grown large this takes longer than an ordinary helper call. On
  bot2 it was cut off after 15 seconds, and the helper was left running beside the Bot that had given up on it. Opening
  the store now has up to 10 minutes, and the helper stops when the Bot stops. While one community's helper starts,
  the Bot keeps answering commands and sending reminders in its other communities.
- **Stopping or upgrading dillad no longer hangs.** On bot2, dillad could not send signals to the Bot, because the Bot
  runs as its own user. Every stop or upgrade waited 45 seconds, and then systemd killed the service. The Bot also
  never received its stop signal or the "installations changed" signal. `dilla.service` now gives dillad's Bot keeper
  `CAP_KILL`, which only the keeper keeps. If the keeper starts without it, the log says
  `signals to the Bot will fail`.
- **The log says why the helper stopped.** `bot installation unavailable` now carries `error_class`, for example
  `timeout`, `helper_exited`, `status_busy` or `launch`. A helper that the Bot stops after a failed call logs
  `bot native helper stopped` with the operation, the class and how the process ended. Neither line includes message
  content or keys.
- **`dillad doctor` run as root no longer reports a problem that isn't there.** It reported
  `FAIL bot: dillad runs as root` for the operator's root shell. It now looks at who owns dillad's data directory, which
  is the user the service runs as.
- **The doctor hints lead somewhere.** They pointed at `dillabot doctor` and `/etc/dillabot/bot.toml`, and bot2's
  installer removes that file. They now point at the Bot's lines in `journalctl -u dilla`.

## Upgrade

1. Take a backup with `dillad backup`. It holds schema 58 and restores with the bot2 or bot2.1 `dillad`. Backups taken
   before bot2 hold schema 55 and restore only with the `dillad` they came from.
2. Run `install.sh --upgrade`, then `install-bot.sh --upgrade`, in one window. Both restart `dilla.service`, and that
   restart is all a running bot2 instance needs: there is no separate step to restart the Bot. `install-bot.sh
   --upgrade` also installs this release's `dilla.service`, which adds `CAP_KILL`. Use the installers: if you only
   swap the binary, the old unit stays, and stops still hang for 45 seconds. The restarts during this upgrade stop
   the running bot2, so they can still take 45 seconds each. Later ones do not.
3. If you marked Bot channels while the Bot's helper was down on bot2, the Bot could not join them. Open
   **Server settings → Bot** and press **Add the Bot again** on each channel that shows "The Bot needs adding to this
   channel again". A channel you mark after this upgrade needs no re-add.
4. Check that the Bot answers. Run `/reminders list` in a Bot channel, or look for `Commands are working` in
   **Server settings → Bot**. `dillad doctor` should show no `bot_health` warning a minute later.

On an instance upgraded from v1, the first start can take a few minutes while the helper removes the v1 groups. During
that time, commands in that community show "The Bot is having trouble". The log shows `bot native helper starting`
when the start begins. Other communities are not held up.

## Operators

- `install-bot.sh --upgrade` from v1 removes the v1 installer's copies in `/var/backups/dillabot` after the upgrade is
  confirmed. Each copy holds the Bot's database key. The v1 units and config are kept in `/var/backups/dilla/bot-v1-*`,
  and `dillad` backups are not touched.
- In an unprivileged LXC container, `journalctl -k` has no kernel log, so it cannot show an out-of-memory kill. Read
  `oom_kill` in `/sys/fs/cgroup/memory.events` instead.
- The Bot's process is named `4` in `ps`, because it is started from an open file. `pgrep -x dillabot` finds nothing.
  List `/sys/fs/cgroup/system.slice/dilla.service/cgroup.procs` instead.
