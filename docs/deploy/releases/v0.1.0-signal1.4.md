# dilla v0.1.0-signal1.4

A hotfix release on top of [v0.1.0-realtime1](v0.1.0-realtime1.md) (which followed
[v0.1.0-signal1.3](v0.1.0-signal1.3.md)), PR #135. It fixes calls that got stuck after the
music Bot joined, makes Bot commands fast, and carries the security fixes deferred from signal1.3. The release includes
`dillad` (with the web client), `dillabot`, their matching core modules, installers and checksums.

## What's fixed

- **Rejoining a call works.** After the music Bot joined a call, a person who left could not rejoin: only the Bot was
  left in the call's encrypted group, the Bot never commits, so the person's old place could never be removed, and
  every rejoin was refused ("I can't join", "joining takes forever"). A call now ends when only bots remain (after two
  checks 30 s apart), and the next person to join starts a fresh one. "End the call if I'm alone" ignores bots.
- **Bot commands no longer wait.** The Bot used to answer commands in the same loop as its background work, behind a
  budget of 3 quick requests and then 1 every 5 s; `/play` takes 6 requests, so commands often took 3–30 s.
  - Commands now run on their own worker and never wait for background work. Commands in the same server still run
    in order.
  - The server-wide budget is replaced by a per-channel limit (10 at once, then 2 per second).
- **Pause and skip are immediate:** about half a second from the click to the audio changing, and a double click
  skips one track.
- **The music panel no longer freezes.** A queue whose saved state and live state disagreed refused every control
  ("revision conflict"), so the title never updated. The Bot now takes the saved state, keeps playing, and never
  refuses a state read.
- **Temporary problems no longer remove tracks.** Only a track that can't play (an invalid or unavailable video, or a
  provider that isn't set up on this server) is skipped. A YouTube rate limit, a network hiccup or a Spotify connection
  failure pauses the queue instead. At most two tracks in a row and five per start are skipped.
- **Skip notices are generic** ("Couldn't play a track. Skipping."). They no longer name the track, so members who
  can't see the voice channel don't see its queue. They are rate-limited and deduplicated.
- **`/resume` always works,** even from a channel where the Bot can't post notices.
- **The Bot reconnects** right away when the server closes its connection for a late heartbeat.

## Versions and compatibility

| Component | This release | realtime1 |
|---|---:|---:|
| Server database schema | 55 | 55 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version (web) | 5 | 5 |

There are no new database migrations. protocol/09 now states that a call ends when only bots remain. Rolling back to
realtime1 is a plain binary rollback; below realtime1, follow realtime1's rollback notes.

## Deploy order

1. Back up as usual. Check that no call is live (`dillad media --rooms --config=/etc/dilla/dilla.toml`); the upgrade
   ends calls.
2. Upgrade `dillad` with `install.sh --upgrade`, then ask everyone to reload their tabs: pause and skip changed in the
   web client.
3. Upgrade `dillabot` with `install-bot.sh --upgrade`, then run
   `sudo -u dillabot dillabot doctor --config=/etc/dillabot/bot.toml --youtube`.

## Known limits

- The Bot handles one command at a time per server (because of its shared event cursor and its encryption helper).
  Up to four servers are handled at once.
- If the Bot hits an error on every attempt at one command, that server's later commands wait behind it. It retries
  with a back-off and logs a warning; a fix follows.
