# dilla v0.1.0-mobile1

A release on top of [v0.1.0-signal2.1](v0.1.0-signal2.1.md). The server accepts the new iOS and Android app, a
preview built from source and not distributed yet, and the web client gains the few screens the app needs. The release
includes `dillad` (with the web client) and `dillabot`. The desktop app is unchanged; see
[Versions and compatibility](#versions-and-compatibility).

## Server

- **New setting `http.mobile_origins`**, default `["capacitor://localhost", "https://localhost"]`: the app's origins
  on iOS and Android. They may:
  - call `/v1/` and `/i/` cross-origin (CORS). A listed origin's preflight is answered with an empty 204 and fixed
    `Access-Control-Allow-Methods` and `Access-Control-Allow-Headers` lists; an actual request gets
    `Access-Control-Allow-Origin` and a fixed `Access-Control-Expose-Headers` list (`X-Dilla-Generation`,
    `Retry-After`). `Access-Control-Allow-Credentials` is never sent: the app uses bearer tokens, never cookies.
    Every response under `/v1/` and `/i/` carries `Vary: Origin`.
  - open the gateway (`/gateway`), as `http.trusted_origins` do.

  Nothing else changes: `/desktop-auth/`, `/gateway` preflights, `/download/` and the browser client's own pages answer
  no CORS, and an unlisted origin gets no `Access-Control-Allow-*` header. CORS is not access control: every route
  still needs its session, and rate limits still meter every actual request. A preflight does no handler work and
  takes no rate-limit token.
- **The origins are never WebAuthn origins.** They are not added to `rp_origins`, so a passkey ceremony from the app's
  origin does not verify; the app uses the system browser and `/desktop-auth/` for passkeys, as the desktop app does.
- **Each entry is checked at start.** An entry must be a whole, lowercase `scheme://host[:port]` origin. A glob
  character, a backslash, an uppercase letter, userinfo, a missing scheme, or a path, query or fragment stops `dillad`
  with an error naming the entry.
- The default applies to an existing instance too: a `dilla.toml` without `mobile_origins` accepts the app after the
  upgrade. To refuse it, set `mobile_origins = []` under `[http]`. See the
  [operator guide](../README.md) (`http.mobile_origins`).

## Web client

- **The mobile shell.** In the app only: an instance picker, **Switch instance** under You and on the boot error
  screen, foreground system notifications through the app, and app wording where the browser says "Reload the page"
  (**Try again**; "Update the app" when the server needs a newer client). Browser and desktop wording is unchanged.
- **Fixed:** an open tab that received its account state again while it restored an update checkpoint could restore
  the checkpoint twice, attaching the saved files twice.

## Versions and compatibility

| Component | This release | signal2.1 |
|---|---:|---:|
| Server database schema | 55 | 55 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version (web) | 5 | 5 |
| Desktop app | 0.1.0-beta.2 | 0.1.0-beta.2 |

There are no new database migrations, and no wire or browser store change. The desktop app does not use
`http.mobile_origins`.

## Deploy order

1. Back up the server database and configuration. Check that no call is live: restarting `dilla` ends calls.
2. Upgrade `dillad` (with its web client) and restart it. Restarting `dilla` also restarts `dillabot`, because the
   `dillabot` unit is `PartOf=dilla.service`.
3. Upgrade `dillabot` from this release, so that both binaries are on the same release, and restart it.
4. Behind a proxy: check that it passes `OPTIONS` requests and the `Origin` header to `dillad` on `/v1/` and `/i/`, and
   that it does not add CORS headers of its own (a duplicate `Access-Control-Allow-Origin` breaks the app).

## Rollback

Rolling back to signal2.1 is a plain binary rollback. Remove `mobile_origins` from `dilla.toml` first if you set it,
because signal2.1 does not know the key. The app then cannot reach the instance; browsers and the desktop app are not
affected.

## Known limits

- The app is a preview built from source: no store, TestFlight or APK builds, no push notifications, no calls in the
  background, no app-icon badges. See [dilla on iPhone and Android](../../user/mobile.md).
- App data is not backed up on Android or iOS, so a new phone signs in with the recovery key as a new device.
- An instance under a base path cannot be reached from the app: the CORS routes are `/v1/` and `/i/` at the root.
- Otherwise the same as [signal2.1](v0.1.0-signal2.1.md#known-limits).
