# dilla v0.1.0-bot2.3

A fix release on top of [v0.1.0-bot2.2](v0.1.0-bot2.2.md). It fixes a Bot helper that closed every time the Bot checked
for new messages, which also left tracks queued twice, and makes a retried `/play` safe. The release includes
`dillad` with the web client, the Bot and its helper. Desktop 0.1.0-beta.4 stays current: there is no new desktop app.

**This release matters if you upgraded from Bot v1.** If you run the Bot, upgrade `dillad` and the Bot together. The
installers do this. There is no data migration and no manual step, apart from the re-add in Upgrade, step 3.

## What's fixed

- **The Bot's helper no longer closes on every check for new messages.** This affected instances upgraded from Bot v1.
  From the first bot2 start, the Bot's helper closed each time the Bot checked for new messages. Under use, the Bot
  stalled, commands failed, and the wait between helper restarts kept growing, up to minutes. This is the cause of the
  silent helper closes seen on bot2 and bot2.1 as well.
  - The log line was
    `bot native helper closed reason=invalidated_decode operation=group_apply kind=result_decode`.
  - The Bot's event log reported its read position past its newest entry. Bot v2 removes some of the log's entries
    when it first starts on an upgraded instance, and the position stayed where it was. The Bot refused that report and
    closed the helper.
  - The event log now never reports a read position past its newest entry, including when the log is empty. Nothing
    is rewritten: a store that was affected is read correctly on the first check.
- **A bad page of events no longer closes the helper.** If a page of events is malformed, only that check fails. It
  logs `detail=` and the helper keeps running.
- **A failed check for new messages now names its stage.** See Operators.
- **Tracks no longer end up queued twice.** On bot2.2 a `/play` could queue its track, then lose its answer when the
  helper closed. You saw a failure, sent `/play` again, and the track was queued a second time. With the helper fix
  above, the answer is no longer lost.
  - In addition, a retried `/play` (the same request, sent again) never queues its track twice. The retry finds the
    track already in the queue and adds nothing. If that track never started, or the player is paused, the retry
    starts playback, as the first `/play` would have.
  - Two separate `/play` commands still queue two items.
  - Tracks that bot2.2 queued twice stay in the queue. Remove one by hand with `/queue remove <item>`. `/skip` skips
    the current track.
  - If the queued track has left the queue since the first `/play` (played, removed or cleared), a replay of that
    `/play` ends as a conflict. It does not queue the track again.

## Upgrade

This is the same as [bot2.2](v0.1.0-bot2.2.md#upgrade).

1. Take a backup with `dillad backup`.
2. Run `install.sh --upgrade`, then `install-bot.sh --upgrade`, in one window. Both restart `dilla.service`. There is
   no separate step to restart the Bot. Use the installers: they upgrade `dillad` and the Bot together.
3. If a Bot channel never finished joining, open **Server settings → Bot**. Press **Add the Bot again** on each channel
   that shows "The Bot needs adding to this channel again." Then look for `bot joined Bot channel group` in
   `journalctl -u dilla`.
4. Check that the Bot answers. Run `/reminders list` in a Bot channel, and look for `Commands are working` in
   **Server settings → Bot**. Then run `dillad doctor`. It should show no `bot_health` warning a minute later.

The line `bot channel group needs the Bot re-added: no Welcome to join it from` means the Bot found no Welcome for that
channel on one pass. It is not a final verdict: it can appear a couple of seconds before `bot joined Bot channel group`
on the same channel. A channel that keeps logging it and never logs `bot joined Bot channel group` needs step 3,
**Add the Bot again**.

If you cannot upgrade yet, there is no reliable workaround. A message posted in a Bot channel only helps if the Bot
already holds that channel's group. Do not count on it.

## Operators

New and changed lines in `journalctl -u dilla`. None of them contains message content, keys, track titles or links.

- **`bot native helper closed`** carries `sub_op=` when the close follows a result the Bot could not decode on a group
  call. `sub_op` is a number. Before bot2.3 every such call showed as `operation=group_apply`, so the number is how to
  tell which call it was. `sub_op=18` is the read of the event log.
- **`bot text command intake deferred`** is logged when a check for new messages fails. It carries `installation_id`
  and `error_class`, and also:
  - `stage`, one of `membership`, `subscribe` or `events`: the step that failed.
  - `detail`, when there is one: `events.cursor_above_high_water` or `events.page_invalid`. Both mean the Bot refused a
    page of events. Neither contains page content.
  - A temporary stop, such as the gateway still reconnecting, logs at Info with `deferred=true`. The next check tries
    again. Any other failure logs at Warn, as before.
- **`bot channel group needs the Bot re-added: no Welcome to join it from`** is not new. It means no Welcome was found
  on that pass, and it can come just before a successful `bot joined Bot channel group`. Only a channel that keeps
  logging it and never logs `bot joined Bot channel group` needs **Add the Bot again**.
- The first music item in a freshly prepared call logs 9 start stages, not 11: `call_token` and
  `call_fields` are skipped because the room's credentials are reused.

## Versions and compatibility

| Component | This release | bot2.2 |
|---|---:|---:|
| Server database schema | 58 | 58 |
| Negotiated wire version | 6 | 6 |
| Desktop app | 0.1.0-beta.4 | 0.1.0-beta.4 |

- There is no schema change and there are no new migrations. Wire 6 is unchanged.
- Upgrade `dillad` and the Bot together, and roll back both together. The installers do this.
- Rolling back to bot2.1 or bot2.2 is a binary rollback. The database stays at `auto_vacuum=INCREMENTAL`, which older
  SQLite reads without trouble.
  - On a database that bot2.2 compacted, bot2.1 never runs the hourly pass that gives free pages back. Free pages
    build up until you upgrade again.
  - A rollback to bot2.2 can bring the helper fault back on instances upgraded from Bot v1. This release does not
    rewrite the Bot's stored read position. Once a new event has been logged after the upgrade, the position is no
    longer past the newest entry, and bot2.2 reads it correctly too.
