# dilla v0.1.0-signal2.1

A fix release on top of [v0.1.0-signal2](v0.1.0-signal2.md). An instance admin's devices could not publish KeyPackages,
so other people and the Bot could not add a new device to a group, and Bot commands were missing on it. This release
fixes that, shows and retries publish failures, and keeps the Bot from getting stuck on devices with no KeyPackages.
The release includes `dillad` (with the web client) and `dillabot`. The desktop app is unchanged; see
[Versions and compatibility](#versions-and-compatibility).

## What's fixed

- **An admin's devices can publish KeyPackages again.** Since v0.1.0-bot1 (2026-10-24) the server refused
  `POST /v1/keypackages` for any account with role flags. That covers every instance admin, including the owner who ran
  `dillad init`. Their devices could not publish, so:
  - other people and the Bot could not add a new device of theirs to a group;
  - Bot commands such as `/play` were missing on those devices;
  - older admin devices could not refill, and would have become un-addable once their last-resort KeyPackage expired,
    around January 2027.

  Accounts without role flags were never affected.
- **Publish failures are shown and retried.** A failed publish appears on the **Key packages** row in Settings →
  Diagnostics, with the count, the time of the last try and the error code. It is retried after 5 s, doubling to at most
  5 min. A reconnect asks the server for the count again.
- **A new device publishes its first batch while it signs in with its recovery key**, before the app is ready.
- **The Bot backs off devices that have no KeyPackages.** Such a device is tried again after 30 s, doubling to 1 h, and
  is logged once at WARN. A stuck device no longer holds back other members' registration. The backoff is kept in
  memory: a `dillabot` restart clears it, so the Bot warns once more for each such device.

## Heal

No revocation and no database edit is needed. Do these steps in this order:

1. Upgrade `dillad` and `dillabot` to this release.
2. Have each affected device quit and relaunch: in the desktop app, quit it fully and start it again; in a browser,
   reload the tab. A resume is not enough. The device then publishes its KeyPackages.
3. Restart the Bot again after the relaunches: `sudo systemctl restart dillabot`. Its per-device backoff lives only in
   memory, so the restart clears it, and the Bot registers the now-published devices within a pass or two. A
   registration the Bot started before this fix is restarted automatically with a fresh snapshot.

Without step 3, a device the Bot had already backed off can wait up to 1 h before the Bot tries it again.

## Server, core and protocol compatibility

- `POST /v1/keypackages` accepts an instance admin's devices. Disabled and deleted accounts, Bot-kind accounts and
  managed Bot sessions are still refused.
- New route `GET /v1/keypackages`. It returns `[ordinary_active_count, has_current_fallback]` for the session's own
  device, where `has_current_fallback` is 0 or 1. Provisional and Bot sessions are refused. An older server answers 404
  or 405, and the client then uses the count from `ready`.
- `GET /v1/devices/{device_id}/keypackage` answers the new code `E_KEYPACKAGES_EXHAUSTED` (404) for a live, listed device
  whose KeyPackage directory is empty. An unknown, revoked or quarantined device still answers `E_NOT_FOUND`. A client
  that does not know the new code still sees a 404.
- The route and the code are additive ([HTTP API](../../../protocol/09-http-api.md),
  [error vocabulary](../../../protocol/02-delivery-service.md)). There is no wire-version or gateway frame change.

## Versions and compatibility

| Component | This release | signal2 |
|---|---:|---:|
| Server database schema | 55 | 55 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version (web) | 5 | 5 |
| Desktop app | 0.1.0-beta.2 | 0.1.0-beta.2 |

There are no new database migrations, and no wire or client store change.

The desktop app is unchanged. It bundles its own copy of the web client, and its windows load that copy for the app's
pages, while data requests go to the server. The server fix alone heals desktop devices: the `0.1.0-beta.2` client
already refills its KeyPackages on every fresh start, and until now that call was refused for admins. It now succeeds.
The new client behaviour (the retries, the **Key packages** row and the first batch at sign-in with a recovery key)
reaches desktop users with the next desktop build.

## Deploy order

1. Back up the server database and configuration. Check that no call is live: restarting `dilla` ends calls.
2. Upgrade `dillad` (with its web client) and restart it. Restarting `dilla` also restarts `dillabot`, because the
   `dillabot` unit is `PartOf=dilla.service`.
3. Upgrade `dillabot` from this release, so that both binaries are on the same release, and restart it. Then run
   `sudo -u dillabot dillabot doctor --config=/etc/dillabot/bot.toml --youtube`.
4. Ask each affected person to quit and relaunch their app, or reload their tab, then restart `dillabot`, as described
   in [Heal](#heal).

## Rollback

Rolling back to signal2 is a plain binary rollback. No data format changed, so there is nothing to migrate. Admins lose
the ability to publish KeyPackages again, which brings back the problem this release fixes. The Bot's backoff is in
memory, so it is simply gone after the rollback.

## Known limits

- Desktop app users on 0.1.0-beta.2 get the server fix, but not the client retry, the **Key packages** row or the first
  batch at recovery-key sign-in, until the next desktop build.
- Server metrics and alerts for devices with empty directories are not part of this release.
- Otherwise the same as [signal2](v0.1.0-signal2.md#known-limits).
