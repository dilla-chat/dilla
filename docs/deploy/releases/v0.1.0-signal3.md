# dilla v0.1.0-signal3

A release on top of [v0.1.0-signal2.1](v0.1.0-signal2.1.md). A message now carries up to ten files instead of four, and
threads work in direct messages and group direct messages. The release includes `dillad` with the web client. It pairs
with `desktop-v0.1.0-beta.3`, whose app bundles this client; see [Versions and compatibility](#versions-and-compatibility).

**Operators:** `dillad init` wrote `max_ciphertext_bytes = 131072` into existing `dilla.toml` files. Set
`[limits] max_ciphertext_bytes = 196608` and restart `dillad`. Until you do, a very large ten-file message is refused
with a clear message (see [Deploy order](#deploy-order)).

## What's new

- **Up to ten files per message.** A message carries up to ten files, up from four, each at most 25 MB as before. Link
  previews are still at most two. The drop zone says "Up to 10 files, 25 MB each.", and an eleventh file is refused
  with "A message carries at most 10 files."
- **A too-large send says so.** A message the server refuses as too large shows "This message is too large to send.
  Send fewer files or remove a link preview." A worst-case message of ten files with two link previews encodes to
  131,643 bytes, which fits the new default.
- **Threads in direct messages and group direct messages.** A DM opens threads in the same thread pane as a channel.
  On a computer the DM header has a **Threads** button, and the side column shows the DM's people where the member list
  is in a channel. On a phone there is no header icon: open a thread from a reply chip, **reply in thread** or search, as
  in a channel. Direct messages sent before this release stay unthreaded.
- **A readable message follows the instance's cap.** The body cap for a readable channel message now follows the
  instance's `max_ciphertext_bytes` instead of a fixed 96 KiB. Reports get 256 bytes of headroom over it.

## Limits

| Setting | signal3 default | signal2.1 |
|---|---:|---:|
| `limits.max_ciphertext_bytes` | 196608 | 131072 |
| `max_frame_bytes` (ciphertext + 512) | 197120 | 131584 |
| Files per message | 10 | 4 |
| File size in a browser | 25 MB | 25 MB |

New installs get the new default. An existing `dilla.toml` keeps its value until you change it.

## Server, core and protocol compatibility

- `max_attachments` is advertised as 10. The protocol documents ([envelope and franking](../../../protocol/04-envelope-and-franking.md),
  [HTTP API](../../../protocol/09-http-api.md)) say ten.
- The default `max_ciphertext_bytes` is 196608, and `max_frame_bytes` is `max_ciphertext_bytes + 512` (197120 by
  default). An instance that changes the cap moves both together.

## Versions and compatibility

| Component | This release | signal2.1 |
|---|---:|---:|
| Server database schema | 55 | 55 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version (web) | 5 | 5 |
| Desktop app | 0.1.0-beta.3 | 0.1.0-beta.2 |

There are no new database migrations and no wire-version or client store change.

The desktop app `desktop-v0.1.0-beta.3` bundles this client. It also carries the client-side KeyPackage retry and the
**Key packages** row in Settings → Diagnostics from [signal2.1](v0.1.0-signal2.1.md). Until desktop users update, the
`0.1.0-beta.2` app shows two things wrongly: a message of more than four files, and a reply in a DM thread, which
appears flat in the conversation.

## Deploy order

1. Back up the server database and configuration. Check that no call is live: restarting `dilla` ends calls.
2. Set `[limits] max_ciphertext_bytes = 196608` in `dilla.toml`, unless you set another value on purpose. dillad never
   rewrites an operator's value.
3. Upgrade `dillad` (with its web client) and restart it. Restarting `dilla` also restarts `dillabot`, because the
   `dillabot` unit is `PartOf=dilla.service`.
4. Ask everyone to reload their tabs, and to update the desktop app to `desktop-v0.1.0-beta.3`.

## Rollback

Rolling back to signal2.1 is a plain binary rollback. There are no migrations, so nothing needs to be undone. Messages
of more than four files, and DM thread replies, sent under this release stay on the server; an older client shows them
as it did before this release.

## Known limits

- Desktop app users on `0.1.0-beta.2` see messages of more than four files, and DM thread replies, wrongly until they
  update.
- Direct messages sent before this release stay unthreaded.
- Otherwise the same as [signal2.1](v0.1.0-signal2.1.md#known-limits).
