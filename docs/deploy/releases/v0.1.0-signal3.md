# dilla v0.1.0-signal3

A release on top of [v0.1.0-signal2.1](v0.1.0-signal2.1.md). A message now carries up to ten files instead of four, and
threads work in direct messages and group direct messages. The release includes `dillad` with the web client. It pairs
with `desktop-v0.1.0-beta.3`, whose app bundles this client; see [Versions and compatibility](#versions-and-compatibility).

**Operators:** `dillad init` wrote `max_ciphertext_bytes = 131072` into existing `dilla.toml` files. Set
`[limits] max_ciphertext_bytes = 196608` and restart `dillad`. Until you do, a very large ten-file message is refused
with a clear message (see [Deploy order](#deploy-order)).

## What's new

- **Up to ten files per message.** A message carries up to ten files, up from four, each at most 25 MB as before. Link
  previews are still at most two. The drop zone says "Up to 10 files, 25 MB each.", and an eleventh file is refused
  with "A message carries at most 10 files."
- **A too-large send says so.** A message the server refuses as too large shows "This message is too large to send.
  Send fewer files or remove a link preview." A worst-case message of ten files with two link previews encodes to
  131,643 bytes, which fits the new default.
- **Threads in direct messages and group direct messages.** A DM opens threads in the same thread pane as a channel.
  On a computer the DM header has a **Threads** button, and **reply in thread** also opens the thread pane in the side
  column. A DM has no member list beside it. On a phone there is no header icon: open a thread from a reply chip,
  **reply in thread** or search, as in a channel. Direct messages sent before this release stay unthreaded.
- **A readable message follows the instance's cap.** The body cap for a readable channel message now follows the
  instance's `max_ciphertext_bytes` instead of a fixed 96 KiB. Reports get 256 bytes of headroom over it.

## Bot fixes

- **A refused Bot registration starts over.** When the core refuses a Bot's registration for a device (the helper
  reports status "invalid"), the Bot now starts over with a fresh admission and a new KeyPackage instead of retrying
  the same refused inputs for ever. It backs off per device, 30 seconds doubling to one hour, and logs one WARN per
  backoff step. The core also reports an expired snapshot as expired before it checks trust, so the existing rotation
  can run.
- **Healing an instance that is already stuck.** Upgrade `dillabot` and nothing else. A wedged device registers within
  one backoff step; no database change, no re-invite and no reset is needed.
- **The command picker keeps the Bot's command list.** The list is kept per community, loaded when the composer
  appears and refreshed every 30 seconds, so typing `/play` right after opening no longer says "No command matches".
  While the first load runs the picker shows "Loading Bot commands…", and Enter on a Bot command that is not listed
  yet waits up to 10 seconds. A first load that fails is retried after 2, 5 and 10 seconds, and opening the picker
  after a failure retries at once. A failure shows in Settings → Diagnostics as `E_BOT_CAPABILITIES`.
- **No more half-second welcome poll.** A client waiting for the Bot's group no longer polls `/v1/welcomes` every
  500 ms. It checks once, then waits for the gateway push with a backoff of 1 to 15 seconds.
- **Poll cards load from the shared list.** A poll card verifies against the same Bot command list, shows "Loading
  poll…" while it does, retries after 2, 5 and 10 seconds, and falls back to the post text if it still cannot verify.
  A post that claims a different Bot shows its text at once.
- **Invites lists unlimited links.** Settings → Invites now includes links with no use limit and links that never
  expire, so they can be revoked from the app. Revoked, expired and used-up links stay hidden.

## Desktop app beta.3

`desktop-v0.1.0-beta.3` also changes the app itself:

- The whole top bar drags the window, not only the part left of search (reported on macOS and Linux; the change applies
  on every platform).
- Quitting with a call or unsent text asks once, "Quit Dilla?" with **Cancel** and **Quit**, and then quits.
  **Restart to update** asks once in the same way. If a window does not report whether it is in use, a plain quit
  offers **Quit anyway**.
- The microphone and camera **Allow** answers are remembered for each instance, separately for the two. A denial is not
  remembered and you are asked again.
- It carries the client KeyPackage retry and the **Key packages** row in Settings → Diagnostics from
  [signal2.1](v0.1.0-signal2.1.md) (#154).

## Design parity

The client matches the Signal prototype more closely:

- Layout: the Settings close button, the voice device selects, the status menu, thread pane spacing, the end of the
  message log, the attachment tray, the search palette, where a member profile card opens, and the column width.
- Body text is weight 400. Settings → Keyboard shows Ctrl and Alt keycaps on Linux and Windows.
- Devices no longer tags this browser with a browser name.
- Music defaults to volume 50 and leave when idle 15m for new installations. Existing settings are unchanged.
- The ban confirm has an optional reason. The kick confirm has none, because a kick records no reason.

## Limits

| Setting | signal3 default | signal2.1 |
|---|---:|---:|
| `limits.max_ciphertext_bytes` | 196608 | 131072 |
| `max_frame_bytes` (ciphertext + 512) | 197120 | 131584 |
| Files per message | 10 | 4 |
| File size in a browser | 25 MB | 25 MB |

New installs get the new default. An existing `dilla.toml` keeps its value until you change it.

## Server, core and protocol compatibility

- `max_attachments` is advertised as 10. The protocol documents ([envelope and franking](../../../protocol/04-envelope-and-franking.md),
  [HTTP API](../../../protocol/09-http-api.md)) say ten.
- The default `max_ciphertext_bytes` is 196608, and `max_frame_bytes` is `max_ciphertext_bytes + 512` (197120 by
  default). An instance that changes the cap moves both together.

## Versions and compatibility

| Component | This release | signal2.1 |
|---|---:|---:|
| Server database schema | 55 | 55 |
| Browser client store schema | 13 | 13 |
| Negotiated wire version (web) | 5 | 5 |
| Desktop app | 0.1.0-beta.3 | 0.1.0-beta.2 |

There are no new database migrations and no wire-version or client store change.

The desktop app `desktop-v0.1.0-beta.3` bundles this client and carries the changes under
[Desktop app beta.3](#desktop-app-beta3), including the client-side KeyPackage retry and the **Key packages** row in
Settings → Diagnostics from [signal2.1](v0.1.0-signal2.1.md). Until desktop users update, the
`0.1.0-beta.2` app shows two things wrongly: a message of more than four files, and a reply in a DM thread, which
appears flat in the conversation.

## Deploy order

1. Back up the server database and configuration. Check that no call is live: restarting `dilla` ends calls.
2. Set `[limits] max_ciphertext_bytes = 196608` in `dilla.toml`, unless you set another value on purpose. dillad never
   rewrites an operator's value.
3. Upgrade `dillad` (with its web client) and `dillabot`, and restart them. Restarting `dilla` also restarts
   `dillabot`, because the `dillabot` unit is `PartOf=dilla.service`. A Bot device stuck on a refused registration
   heals within one backoff step of the new `dillabot` running.
4. Ask everyone to reload their tabs, and to update the desktop app to `desktop-v0.1.0-beta.3`.

## Rollback

Rolling back to signal2.1 is a plain binary rollback. There are no migrations, so nothing needs to be undone. Messages
of more than four files, and DM thread replies, sent under this release stay on the server; an older client shows them
as it did before this release.

## Known limits

- Desktop app users on `0.1.0-beta.2` see messages of more than four files, and DM thread replies, wrongly until they
  update.
- Direct messages sent before this release stay unthreaded.
- Otherwise the same as [signal2.1](v0.1.0-signal2.1.md#known-limits).
