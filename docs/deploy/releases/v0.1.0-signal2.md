# dilla v0.1.0-signal2

A release on top of [v0.1.0-signal1.5](v0.1.0-signal1.5.md). It finishes the Signal redesign of the web client (wave B),
makes pause and play on the music Bot fast, fixes the desktop app's sign-in window and errors, and lets an instance
send browser visitors to the desktop apps through verified download links. The release includes `dillad` (with the web
client), `dillabot`, their matching core modules, installers and checksums. The matching desktop build is
`desktop-v0.1.0-beta.2`.

## What's new

### The Signal redesign, wave B

- **Commands.** `/` opens every available command in Built-in and Bot groups, with icons and descriptions. Arguments
  are inline chips with keyboard navigation and suggestions. Errors appear in the command bar and mark the chip at
  fault. Escape keeps the draft, multi-line code included. Reminder previews use the browser's time zone, and `/me`
  keeps its author.
- **Private results.** Inline cards show Working, Done, Failed and Not confirmed. Bot commands carry the Bot's name
  (Glenn by default) and a BOT tag; built-ins carry dilla and the D tile. `/kick` and `/ban` ask for confirmation and
  log a row. Only Ban shows Duration and Reason, and a permanent ban has no end date. Cancelling either adds a Not
  confirmed row. A confirmation fires once.
- **Sign-in.** The six-digit code boxes take typing, paste and autofill, and submit on the sixth digit. Passkeys are
  offered in the username field's autofill where the browser supports it; other browsers show a passkey button.
  Back, the backup-code and passkey alternatives and the done panel follow the Signal flow. A passkey used after a
  password or an identity-provider sign-in must belong to that account.
- **Sign-up.** Six steps: invite, account, recovery key, second factor, code and done. The account is created only
  after **I saved it** on the recovery key step. **Print** and **Save as file** keep the key; there is no Copy button.
  Backup codes appear on the done step (behind **Show** on phones) and must be acknowledged before **Open dilla**.
  New and changed passwords need at least 12 characters; existing shorter passwords still sign in.
- **Voice menus.** Your own menu has Mute, Deafen and their shortcuts, Profile, Move to with room counts, and Leave
  voice. Other people's menus offer Profile, Message, Mention, Copy username and Edit roles where allowed, with local
  volume and mute. The AFK row opens its page: **Go AFK** leaves your call, **Come back** opens a text channel you can
  write in. Phones are never moved for inactivity.
- **Polls.** A New poll dialog with answers, duration and multiple choice, and a card with bars, your votes, named
  voters and time left. Voters are counted once across answers. A vote that may not have counted says so, and only
  that answer can retry.
- **Conversations.** Threads opens the last thread you opened in a channel, otherwise the most recently active one.
  Upload toasts, attachment cards, code-only toolbars, phone message actions and emoji pickers use the Signal look.
  GIFs in direct messages are opt-in, with a privacy notice.
- **The rest of the shell.** Settings, reminders, status menus, phone navigation and the window chrome follow the
  prototype. The parity tooling compares the running app with the prototype in every state.

### The music Bot

- **Pause and play are fast.** Pause holds the YouTube stream and sends silence; play continues from the same second,
  well under a second later. Before, play downloaded the track again and restarted it, which took about 10 seconds.
- **A long pause frees the stream.** After 10 minutes paused the Bot lets the stream go. A later play starts where you
  paused, a few seconds slower.
- **Starts you trigger go first.** Play, skip and a resume after a long pause run ahead of the Bot's background work.
- **Adding a track no longer fails with a conflict** when the music panel is slightly out of date.
- **A restart never resumes a stale position.** A queue the Bot saved while playing restarts its track from the
  beginning after a Bot restart; a queue saved while paused keeps its place.
- The Bot's debug log shows where a YouTube start spends its time (no URLs or titles).

### The desktop apps

- **One window.** Connecting to an instance closes the instance picker; the app no longer leaves it open beside the
  main window.
- **Clear errors.** Passkey or identity-provider sign-in from the desktop app against an instance without desktop
  sign-in says that the instance needs an update, and too many attempts say to wait.
- **Desktop in the device list.** Desktop devices keep browser-tier custody (tier 1) and show as Desktop in the device
  list on that device; native custody for the desktop app is planned. The own row says where it runs ("Desktop ·
  macOS", "Browser · Firefox"). The label is informational, not a security check, and is not sent to the server, so
  other devices list it by its name only.
- **A styled sign-in page.** The page the app opens in the system browser for passkey and identity-provider sign-in
  uses the Signal design. Its stylesheet is served from the same origin, and the strict Content-Security-Policy stays
  (`style-src 'self'`).

### Desktop-only mode and the download routes

An instance can send its browser visitors to the desktop apps. Start `dillad serve` with `--desktop-downloads` (off by
default):

- **What browser users see.** Opening the site shows a Download Dilla page instead of the web client, with a button
  for Linux (AppImage, DEB, RPM, AUR recipe), Windows x64 and macOS on Apple Silicon. There is no macOS Intel build.
  Invite links offer to open the invite in the desktop app (`dilla://`) and the downloads.
- **Where the buttons go.** Each button is `/download/<platform>` on the instance: `linux-appimage`, `linux-deb`,
  `linux-rpm`, `linux-aur`, `win-x64` and `mac-arm64`. `dillad` reads the desktop beta feed
  (`https://dilla-chat.github.io/dilla/beta/desktop-beta.json` and its `.sig`). It verifies the signature under the
  metadata keys the desktop app pins, checks the feed has not expired, and redirects to that release's asset on
  `github.com/dilla-chat/dilla/releases/download/desktop-v<version>/`. A verified feed is cached for 10 minutes. If the
  feed cannot be fetched or does not verify, the page says the download is unavailable and links to the releases page.
  Nothing unverified is ever redirected to. Without the flag, `/download/<platform>` is a 404.
- **Moving from the browser.** **Open existing browser device for migration** gives the browser client back for one
  hour, on that browser only, so people can check their conversations before they switch. **End migration access**
  ends it early. Browser data stays in the browser and is not copied to the desktop app.
- **The desktop app is a new device.** Signing in on desktop needs the password, the second factor and then the
  52-character recovery key to enrol the new device. The password alone cannot unlock the keys. Messages sent before
  the desktop device joined are not shown on it. Anyone without their saved recovery key should keep their browser
  device.

## What's fixed

- **The Bot shows up as soon as it is enabled.** Enabling the Bot in a server now tells everyone online to reload the
  member list, so the Bot appears in it and command results carry its name right away. Before, it appeared only after
  a refocus, reconnect or reload. Removing the Bot updates the list the same way.
- **The Linux desktop app no longer refuses to start on a busy machine.** The sandbox check could report its helper
  processes as left behind when they had all been stopped, and the app then refused to start. Nothing was ever left
  running.
- The Bot's `sender trust refresh failed` warning is gone.
- The desktop shell refuses a passkey autofill request instead of opening the system browser when a field is focused.

## Server, core and protocol compatibility

- New or changed passwords need 12 Unicode code points. Account creation and password changes check the length first.
- Passkey login begins have their own rate buckets: `passkey_begin` per address (default 0.2/s, burst 10) and
  `passkey_begin_net` per IPv4 /24 or IPv6 /48 (default 1/s, burst 40). Beginning autofill spends no password attempt.
  A finish for an absent, expired or spent ceremony does not charge the login failure budget.
- Discoverable login ceremonies live 120 seconds; registration and step-up ceremonies 5 minutes.
  `auth.webauthn.max_open_logins` (default 10000) and `max_open_per_user` (default 5) cap open ceremonies; at the cap
  the oldest in that scope is evicted.
- A successful password login that still owes a factor may carry a third `passkey` flag; a passkey finish accepts an
  optional third first-factor assertion (password or OIDC), and another account's passkey answers 403
  `E_PASSKEY_OTHER_ACCOUNT` ([HTTP API](../../../protocol/09-http-api.md),
  [error vocabulary](../../../protocol/02-delivery-service.md)). Both are additive; older clients and requests keep
  their meaning.

format.

## Deploy order

1. Back up the server database and configuration. Check that no call is live: the `dillad` restart ends calls.
2. Upgrade `dillad` (with its web client) and restart it. Keep any rate or ceremony-cap overrides, or use the defaults
   above.
3. Ask everyone to reload their tabs.
4. Upgrade `dillabot` from the same release, restart it, and run
   `sudo -u dillabot dillabot doctor --config=/etc/dillabot/bot.toml --youtube`.
5. Desktop-only mode, when you want it, last:
   - wait until `desktop-v0.1.0-beta.2` is published and the beta feed names it;
   - make sure the reverse proxy passes `/download/*` (and `/desktop-auth/*`, as for signal1.5) to `dillad`. A proxy
     that forwards the whole host needs no change;
   - add `--desktop-downloads` to `dillad serve`, for example with `systemctl edit dilla` overriding `ExecStart`, then
     restart `dillad`;
   - check that `curl -sI https://<your host>/download/linux-appimage` answers `302` with a `desktop-v0.1.0-beta.2`
     location.

## Rollback

Rolling back to signal1.5 is a plain binary rollback: there are no migrations. Passwords set under the 12-character
rule still work. Turn `--desktop-downloads` off before rolling back: signal1.5's download page links a release alias
that no longer exists.

## Known limits

- The download routes follow the beta channel only.
- Showing who reacted in a reaction's tooltip is wave C.
- A cold Bot start (the first `/play`, a skip, the end of a track) still takes several seconds.
- Otherwise the same as [signal1.5](v0.1.0-signal1.5.md#known-limits).
