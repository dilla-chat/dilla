# dilla v0.1.0-bot2

A release on top of [v0.1.0-signal3](v0.1.0-signal3.md). It redoes how the Bot works. A Bot command now goes to the Bot
in one step and the answer comes straight back, music starts faster, anything that can send an HTTPS request can post
into a channel through the Bot, and the Bot's health is a real test of the command path. The release includes `dillad`
with the web client, the Bot and its helper, and it pairs with the desktop app built from the same release.

**Everyone must update the desktop app.** This release is wire 6 and keeps no compatibility with older apps (see
[Versions and compatibility](#versions-and-compatibility)). **Operators:** read [Upgrade order](#upgrade-order) first.
Upgrade `dillad`, then the Bot, in one window. The upgrade retires `dillabot.service`.

## What's new

- **One step per command.** A command is sent to the Bot as one request over the socket the app already has, and the
  Bot's answers come back on it. The picker's list of commands is kept on your device and updated by the server, so it
  never shows "Loading Bot commands…". The app no longer polls for answers, and no longer asks the Bot what it can do
  before each command.
- **Faster music.** The Bot looks a track up and prepares the next one in advance, so a track you queued starts without a
  gap and one you played a moment ago starts quickly. **Server settings → Music** lists the **Last 20 music starts**,
  each with the time from the command to the first sound.
- **Bot channels.** The Bot joins only the text channels an admin marks as **Bot channels** (**Server settings →
  Channels**, **edit**, **Bot channel**), and posts only there. See [Bot channels must be marked](#bot-channels-must-be-marked).
- **Webhooks.** On **Server settings → Bot**, an admin creates a webhook for one Bot channel and gets an address once:
  `https://<instance>/hooks/<id>/<secret>`. A `POST` with `{"text": "…"}` (up to 4000 bytes; `username` and `avatar_url`
  are optional; Discord's `content` is read too) is answered `204` and shows in the channel as "via webhook <name>". A
  webhook takes 30 posts a minute with a burst of 5. It cannot run commands or ping anyone, and `@everyone` works only
  if the admin turned on **Allow @everyone**. The server never stores the body. See
  [Bot commands](../../user/bot-commands.md#webhooks).
- **Greyed commands say why.** A command that cannot run stays in the picker with its reason: "Mark a channel as a Bot
  channel first", "The Bot is offline since 06:24" or "The Bot is having trouble since 06:24".
- **Honest health.** Every minute the Bot sends itself a real command through the server and back. **Server settings →
  Bot** shows "Commands are working", "Commands failing since 06:24" or "The Bot is offline since 06:24", with the
  Bot's command key. `dillad doctor` prints `commands failing since <time>` too.
- **The Bot ships with `dillad`.** There is no `dillabot.service`, no `/etc/dillabot/bot.toml` and no URL to set.
  `dillad` runs the Bot as its own sandboxed child, as the `dillabot` user, and they talk over a Unix socket. Its settings
  are `[bot]` in `dilla.toml`.
- **Everything after sign-in goes over the socket.** Sending, editing, groups, communities, settings and the rest are
  requests on the app's WebSocket instead of separate HTTPS requests. While the socket is down the app queues them
  and sends them in order when it reconnects. Sign-in, file transfers, the public pages and webhooks stay on HTTPS.
  An in-flight request cap of 64 per connection keeps one app from flooding the server; over it the app waits and
  sends again.

## What was removed

- **AutoModeration.** It is gone, with its settings page, its stored configuration and its server routes. The
  upgrade deletes the stored settings and logs a line. Warnings, timeouts, kicks, bans, the moderation log and
  evidence stay.
- **Interaction groups.** The private group each member needed with the Bot is gone, with the checks that kept it
  working. The Bot no longer sits in every channel's group.

## Upgrade order

1. **Back up first.** Take a `dillad backup` and keep it.
2. **`dillad` and the web client first, then the Bot, in one window:**

   ```sh
   sudo sh install.sh --upgrade --yes
   sudo sh install-bot.sh --upgrade --yes
   ```

   Between the two scripts the Bot is down, because the new `dillad` refuses a v1 Bot. `--yes` lets each script restart
   `dilla` with calls live (restarting `dilla` ends them). Leave it off to have a script stop while a room has people in
   it. Both scripts check each downloaded file against `SHA256SUMS`, log every step, and put every changed file back if
   a check fails.
3. **Then the desktop app.** Release the desktop app after `dillad`, as with signal3. A desktop app that is not updated
   shows "Update dilla to continue" and its **Update** button. A browser tab reloads on its own.
4. **Check `bot.toml` for custom settings.** The upgrade moves your v1 `bot.toml` to the backup (below). A custom
   `reconcile_interval` or `[rate_limits]` in it is not carried over: the Bot polls nothing now and its rate limits are
   built in. Read the backup before you rely on the defaults.
5. **Mark the Bot channels.** See below.

The Homelab-style upgrade is exactly this: `install.sh --upgrade`, then `install-bot.sh --upgrade`, in one window with
`--yes`.

### What the Bot upgrade does

`install-bot.sh --upgrade` retires `dillabot.service` and leaves a backup:

- It backs up `dillabot.service`, `/etc/dillabot/bot.toml` and the `dilla.service` it replaces to
  `/var/backups/dilla/bot-v1-<UTC timestamp>/` (root only). The backup holds no key and no credential.
- It stops and disables `dillabot.service`, removes it and `/etc/dillabot/bot.toml`, installs this release's Bot,
  helper and `dilla.service`, and sets `[bot] enabled = true` in `dilla.toml`.
- It moves the runtime credential, unchanged, to `/var/lib/dillabot/runtime.token`. The Bot's state in
  `/var/lib/dillabot/<installation>` (its keys, reminders, polls, settings, music queue and moderation evidence) stays
  where it is.
- It restarts `dilla` and checks that the Bot runs as `dillabot` with no capability for 15 seconds. If any check fails
  it puts the v1 Bot back.
- A second run changes nothing and says so.

A killed run can be started again: it finds the pending backup and resumes. A root-owned `runtime.token` (after a
restore done as root, for example) is refused, not repaired: run
`sudo chown dillabot:dillabot /var/lib/dillabot/runtime.token`, then run the script again.

### Bot channels must be marked

No channel is marked for you. After the upgrade the Bot leaves every channel's group. Welcome messages, scheduled
announcements, role panels, polls and the music card keep their settings but post nothing until an admin marks a Bot
channel and picks it for each one. **Server settings → Bot** shows them as "Needs a Bot channel". Posts the Bot made
before stay where they are. A poll in a channel that is not a Bot channel stays readable and takes no more votes.

### Known behaviour

- **A mark that races a Bot pass can show "needs re-add".** If an admin marks a channel while the Bot is restarting or
  reconciling, **Server settings → Bot** can say "The Bot needs adding to this channel again." Press **Add the Bot
  again**. It takes a minute at most.
- **A just-marked channel answers webhooks `503` for a few seconds.** Until the Bot has joined the channel, a webhook
  `POST` is answered `503` with `Retry-After: 5`. Senders that retry get through.
- **A `503` can mean the post already happened.** If the Bot posted and its acknowledgement was lost, a sender that
  retries posts twice.
- **The new binary refuses a database dump from before this release.** On Postgres, `dillad restore` refuses a backup
  taken by an earlier release, because migration 00058 dropped tables that dump names. Take a new backup after the
  upgrade, and restore an older one with the binary that took it.

## Operators

- **Redact `/hooks/*` in your reverse proxy's access log.** A webhook's secret is in its URL. `dillad` logs only the
  route pattern, but a proxy logs full URLs by default, and anyone who reads those logs can post to the channel. See
  [Dilla Bot installation](../README.md#dilla-bot-installation) for nginx and Caddy examples. A secret that reached a log
  should be rotated on **Server settings → Bot**.
- **`dillad doctor` has a Bot leg.** It checks the Bot's user, binaries and state directory, and prints
  `commands failing since <time> (community <id>)` when a Bot's commands fail. `install.sh` and `install-bot.sh` check
  that the running Bot holds no capability.
- **Cold backup and restore** now stop `dilla` and archive only `/var/lib/dillabot`. The procedure is in
  [Dilla Bot installation](../README.md#dilla-bot-installation), and the coordinated acceptance run is in
  [Dilla Bot backup and restore acceptance](../bot-backup-restore-acceptance.md).
- **State owned by the wrong user.** After a restore as root, give `/var/lib/dillabot` back to `dillabot`:
  `sudo chown -R dillabot:dillabot /var/lib/dillabot`.

## Versions and compatibility

- **Wire 6.** `dillad` offers wire 6 only. An older desktop app or a browser tab from before the upgrade is refused with
  `E_UPGRADE_REQUIRED` and shows "Update dilla to continue" (desktop) or reloads (browser). The Bot negotiates 6 too.
  There is no fallback to older clients.
- **Release order.** `dillad` and the Bot first, then the desktop app.
- **Migrations.** 00056 (wire 6 sessions), 00057 (the Bot's catalog, command keys, Bot channels and webhooks) and 00058
  (drops the v1 interaction and AutoModeration tables and deletes kind-3 groups) run when `dillad` starts, after a
  pre-migration backup.

## Rolling back

A rollback to signal3 needs more than the old binary. Put the signal3 `dillad`, the signal3 `dillabot` and
`dillabot.service` back, and use the signal3 desktop app: a wire-6 app cannot talk to a signal3 server. The interaction
groups come back by themselves, because the old Bot and apps register them again. The migrations have downs; the down
of 00058 recreates the dropped tables empty. Stored AutoModeration settings and kind-3 groups were deleted by the
upgrade and do not come back. The backup in `/var/backups/dilla/bot-v1-<UTC timestamp>/` has the v1 unit, `bot.toml`
and `dilla.service`, and the database you backed up in step 1 is the one to restore on Postgres.

A rollback also forgets this release's Bot setup: the down of 00057 drops every Bot channel mark, every webhook and
the command-key publications. Webhook URLs stop working (their secrets are gone, so integrations need new URLs after
the next upgrade), and channels must be marked as Bot channels again.

## Known limits

- Outgoing integrations (a command that calls an admin's URL, such as `/weather`) are not in this release.
- Music comes from YouTube only.
- The real capability chain of the keeper (that the Bot holds no capability) is checked by the installers on the
  host. A host where it fails reports `RED bot: …` and the fresh install turns the Bot off; the upgrade puts the v1
  Bot back.
